## Product intent

Today every online action of the local player travels server-and-back before it shows on screen — `RTT/2 + SNAPSHOT_INTERVAL_MS` minimum on a perfect connection (`33 ms` at `30 Hz`), and several hundred ms on a normal home network. For a fast-paced PvP arena (036) and competitive-feeling co-op (037) that delay is felt as input lag and breaks the fluency the player has come to expect from local play. Story 034 extracted the simulation runtime into `src/shared/sim/**` so the same code runs identically under the browser worker (local-authoritative) and the Node arena host (online-authoritative). This story spends that work to deliver Source-style ("Quake/Fortnite") client-side prediction: the same shared `SimulationCore` runs on the client itself as a non-authoritative predictor for the local player only, applying input immediately and reconciling against authoritative snapshots when they arrive. Movement, own-projectile spawn, own-projectile motion, and movement-affecting status all feel local; the server stays authoritative for everything that matters (hits, HP, deaths, level changes, projectile lifetime, drops, encounter and boss progression). Other players are not extrapolated — that direction stays explicitly out of scope unless a future story revisits it with measured justification.

## Player-facing

- Sees: in online play, the local player's movement reacts to WASD/touch input immediately, within a single render frame, regardless of network conditions.
- Sees: clicking LMB (or the mobile fire button) makes the player's bullet visibly leave the muzzle in the same render frame, not after a network round trip.
- Sees: the predicted bullet flies smoothly along its full trajectory, in the same way bullets fly in offline play.
- Sees: when the player's form changes in PvP (level up to a higher slime, become the boss), the new movement speed and weapon take effect immediately on the local screen — no "I leveled up but I'm still moving like the old form for half a second" interval.
- Sees: when the local player gets hit by a slow puddle or other movement-affecting status, the slowdown feels local — no "I'm in the puddle visually but still moving fast for half a second" interval.
- Sees: at the moment authoritative state corrects a small mispredicted local position (rare, e.g. wall clip near a corner), the correction blends smoothly over a short window rather than snapping.
- Sees: at the moment authoritative state issues a large change for the local player (PvP respawn into a corner, downed transition into ghost in co-op, revive back to alive, level-up form change with teleport), the screen snaps cleanly to the new state without trying to blend across the teleport.
- Sees: other players continue to move smoothly through snapshot interpolation, just as before.
- Sees: no change to local single-player play — campaign, training, dungeon, and sandbox behave identically.

## Technical

Source-style client-side prediction recorded as [online-client-prediction.md](../design/online-client-prediction.md). The shared `SimulationCore` from `src/shared/sim/**` runs on the client inside the existing browser simulation worker as a mutually exclusive **online-predictor** mode against the existing **local-authoritative** mode; one core at a time, gated by `UiShell` phase ([main-ui-shell.md](../design/main-ui-shell.md)). The predictor's `EntityStore` contains the local Player + own in-flight Projectiles only (the "(a) self-only" world view chosen explicitly over a full-mirror alternative). The shared `MovementSystem` produces predicted positions; the shared `CombatSystem` firing/projectile-motion phases produce predicted own-projectile spawn and motion; the shared `StatusEffectSystem.resolveMovementSpeedMultiplier` consumes `PlayerSnapshot.statusEffects` from the latest authoritative snapshot. The predictor never publishes `RuntimeEvent` outwards, never publishes HP/death/level changes, and never decides hits — predictor invariants enforced by a new boundary test.

Reconciliation: every authoritative snapshot rolls back the predictor's self-Player runtime state to the snapshot's `PlayerSnapshot` for `selfPlayerId`, rolls back self-Projectile state to the set of `ProjectileSnapshot`s with `ownerId === selfEntityId` matched by `spawnInputSequence`, trims the input buffer of every entry whose `inputSequence <= snapshot.lastInputSequence[selfPlayerId]`, and replays the remaining buffered inputs through shared systems against the predictor's runtime state. Predictor `simTime` after replay equals `snapshot.simTimeMs + replayedTickCount * SIM_STEP_MS`. Reconciliation is event-triggered for transitions (snap on `playerSpawn`/`playerDowned`/`playerRevived`/`host:levelUp`/predicted-fire-rejected timeout, snap on `formArchetypeId` change) and threshold-blended for small drift (`100 ms` linear blend on position delta above `0.05 wu` epsilon).

Form changes are reactive only — the predictor never attributes a kill itself. On `host:levelUp` for self, or on a snapshot `PlayerSnapshot.formArchetypeId` change for self, the predictor snaps to new form stats looked up from shared content (`content/enemies.md`, `content/bosses.md`) by `formArchetypeId`, exactly mirroring the host's `pvpKillToLevelOps` lookup ([online-session-hosting.md](../design/online-session-hosting.md)).

Wire/snapshot extensions, all additive, are recorded in [snapshot-shape.md](../design/snapshot-shape.md) and [input-commands.md](../design/input-commands.md): every input envelope carries `inputSequence: number` (monotonic per session, owned by the client side); every authoritative snapshot carries `Snapshot.lastInputSequence: { [playerId]: number }` (Node host-produced; local play emits an empty object); every projectile snapshot carries `ProjectileSnapshot.ownerId: number` and `ProjectileSnapshot.spawnInputSequence: number | null`; every player snapshot carries `PlayerSnapshot.statusEffects: ReadonlyArray<PlayerStatusEffectSnapshot>` shaped per the runtime `ActorStatusEffect` types minus server-only damage timing fields. The Node arena host validates incoming `inputSequence` (strictly greater than last applied for that actor; out-of-order intents dropped with a warning) and tracks the last applied per actor ([online-session-hosting.md](../design/online-session-hosting.md)).

Cosmetic hit feedback (impact sparks, slime splash) on visual coincidence between a predicted own projectile and an interpolated other entity is permitted as presentation-only — it must not despawn the predicted projectile. Despawn is server-driven; the standard Source-style guarantee against phantom projectiles holds.

## Out of scope

- Extrapolation of other players, enemies, bosses, drops, companions — explicitly forbidden by [simulation-timing.md](../design/simulation-timing.md), and a known artifact source on direction changes.
- Client-side hit determination / despawn prediction for own projectiles — the predictor predicts spawn and motion only; lifetime end is server-driven. Phantom projectile risk is not taken.
- Rollback/GGPO-style netcode where every client predicts every actor — separate paradigm, not adopted here.
- Server-side lag compensation (rewind-for-hits) — separate technique, not required for slow projectile combat in this game.
- Companion prediction — companion AI in co-op stays interpolated from snapshots in 038. A future story may add "companion follows predicted self" if the visible owner-companion lag is judged unacceptable.
- Snapshot delta encoding, compression, or any other transport optimization.
- Per-tick "input frame" protocol — current per-command send-on-change is preserved.
- Any change to combat hit determination, projectile motion authority, HP, death, level rules, drop pickups, encounter/boss progression — server stays the source of truth.
- Local single-player play — unchanged.

## Acceptance

- In online PvP and online co-op, the local player's rendered position responds to movement input within a single render frame, independent of network RTT.
- The local player's predicted bullet appears at the muzzle and starts flying within a single render frame after `fire: start` input, independent of network RTT.
- Form changes for the local player (`host:levelUp` in PvP, future hostable form changes elsewhere) take effect on the local screen within a single render frame after the event arrives — new movement speed, new weapon, new visual.
- A movement-affecting status effect on the local player (e.g. `slow`) is reflected in the predictor's local replay starting from the first authoritative snapshot that carries the effect.
- Other players' rendered motion is unchanged from current behavior (snapshot interpolation only, no extrapolation).
- Server-side gameplay authority is preserved end-to-end: a deterministic test or scenario shows that a client cannot retain an advantage by mispredicting its position, fire, or form when the server disagrees.
- A small position divergence between predicted and authoritative position (above the `0.05 wu` epsilon, below transition-event thresholds) resolves smoothly over the recorded `100 ms` blend window — no snap, no permanent offset.
- A large position divergence triggered by a transition event (`playerSpawn`/`playerDowned`/`playerRevived`/`host:levelUp`/`formArchetypeId` change in snapshot) resolves by snap — no blend across the teleport.
- A predicted fire that the server rejects (cooldown still active on server, actor died/disconnected/in invulnerability when input applied) is removed by snap within one ack window after the input is acknowledged with no matching authoritative projectile.
- The predictor never emits `RuntimeEvent` outwards as authoritative facts — covered by a boundary test enumerating the forbidden output kinds and modes.
- Under simulated network conditions (browser dev-tools throttling at `100 ms` and `200 ms` RTT), the local player's movement and own projectile fire feel as responsive as offline play; other players show the same interpolation lag as before.
- All existing local single-player and online tests pass without behavioral regression. The new snapshot fields (`lastInputSequence`, `ProjectileSnapshot.ownerId`, `ProjectileSnapshot.spawnInputSequence`, `PlayerSnapshot.statusEffects`) ride through the local single-player path without breaking HUD/render — covered by a regression test in the same place that covered the `weaponHud` migration in 036.
