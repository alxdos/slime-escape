# Stories

Vertical playable slices of the project. One file = one story. Every story must deliver a demoable feature to the player. Format and template — [_template.md](_template.md).

- File name: `NNN-shortname.md`. The number increases by `+1` and is never reused.
- Numbering defines the recommended reading order. Execution order may differ: a story can be skipped and picked up later — this is reflected in `Status`.
- Statuses: `planned` | `in-progress` | `done` | `blocked` | `deferred`.
- Markers in task tables and in the story index: `[ ]` planned, `[/]` in-progress, `[x]` done, `[-]` blocked, `[~]` deferred. In the story header (`- Status:`) the status stays as a plain word.
- `blocked` means the story cannot move forward because of an external or technical obstacle; `deferred` means we intentionally postpone it until a trigger or higher priority appears.

## Workflow

Separation of concerns:

- **A story** answers "what we are building" (a feature for the player) and "what we touch" (systems, protocols, files). It stays short.
- **`design/`** answers "how exactly things are wired" inside a given area. Files are grouped by area and evolve across stories.

Flow:

1. Before starting a story, read all of its `Related` files from `design/`.
2. If a design decision is created or changed during the work:
   - find the matching `design/<area>.md` file and update it, or create a new file for a new area;
   - bump the `Updated` field, and `Status` if needed;
   - link to it from the story `Related` and mention it briefly in `Technical`.
3. Detailed reasoning, alternatives, and edge cases live only in `design/`. The story links to it instead of repeating it.
4. Before closing a story, make sure every touched `design/` file is listed in `Related` and that the index [../design/README.md](../design/README.md) is up to date.

Rule: if a decision affects future stories, it must land in `design/` — not stay buried in a single story.
