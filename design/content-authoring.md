## Context

Сегодня контент игры (архетипы врагов, оружие, дроп, боссы, игрок, арены, preset-ы, сборка сессии, маппинги аудио на архетипы) живёт как TS-литералы, разнесённые по `src/shared/content/**` и `src/main/audio/AudioMappings.ts`. Любая правка баланса = правка TypeScript: PR-ревью смешивает «изменили число» и «изменили логику», а у геймдизайнера нет отдельной поверхности, которая бы позволяла менять параметры, не открывая код.

Нужна авторская поверхность для геймдизайнера со следующими свойствами:

- один Markdown-файл = один контентный область (slimes/enemies, sessions, weapons, …);
- генератор времени сборки превращает MD в те же TS-литералы, что и сейчас, без изменений в потребителях;
- рантайм-контракты (`EnemyArchetype`, `AudioMappings.EnemyAudioMapping`, …) и их валидаторы не меняются;
- ошибка в MD не приводит к молчаливой подмене или частичному писанию: либо всё валидно и переписано атомарно, либо файлы остаются как были и сборка падает с понятным сообщением;
- сгенерённое не дрейфует от MD: нет «MD сказали одно, в репозитории сгенерённое другое».

Решение фиксирует устойчивые правила этого слоя; конкретный набор полей конкретной области (имена колонок, какие группы балансных таблиц, и т. п.) принадлежит самой области и её истории, а не этому документу.

## Decision

### Источник правды и слои

- Для каждой контентной области, которой управляет MD-источник, существует **один** файл `content/<area>.md` в корневой директории `content/`. Это единственное место, где геймдизайнер меняет данные этой области. Первая такая область — `content/enemies.md` (включая стационарные мишени). Последующие области (`weapons`, `drops`, `bosses`, `players`, `sessions`, `arenas`, `presets`) добавляются отдельными историями, каждая со своим `content/<area>.md`. На момент этой ревизии живы области `enemies`, `weapons`, `drops`, `bosses` (после 011/012), `players` (история 013) и `sessions` (история 015).
- Одна область может производить несколько выходных пар `<area>.generated.ts` рядом с разными потребителями (см. ниже). На момент этой ревизии:
  - `enemies` → `src/shared/content/enemies.generated.ts` + `src/main/audio/enemyAudio.generated.ts` + `src/main/render/enemyVisuals.generated.ts`;
  - `weapons` → `src/shared/content/weapons.generated.ts` + `src/main/audio/weaponAudio.generated.ts` + `src/main/render/projectileVisuals.generated.ts` (новая пара с истории 017);
  - `drops`   → `src/shared/content/drops.generated.ts` + `src/main/render/dropVisuals.generated.ts` (новая пара с истории 017);
  - `bosses`  → `src/shared/content/bosses.generated.ts` + `src/main/audio/bossAudio.generated.ts` + `src/main/render/bossVisuals.generated.ts`;
  - `players` → `src/shared/content/players.generated.ts` + `src/main/render/playerVisuals.generated.ts`;
  - `sessions` → `src/shared/content/sessions.generated.ts`.
- Один MD-файл может производить **один или несколько** сгенерированных `.ts`-файлов, размещённых **в том слое, который данные потребляет**, а не в одном «свалочном» каталоге generated. Для области enemies это:
  - балансные/контентные поля `EnemyArchetype` → `src/shared/content/enemies.generated.ts` (`content library`, sim-сторона);
  - аудио-маппинг (`hit/death sampleIds`, `voice` sampleIds + интервалы) → `src/main/audio/enemyAudio.generated.ts` (presentation, main-сторона).
- Это разделение обязательно и фиксирует границу из [content-boundaries.md](content-boundaries.md): аудио — это presentation, не часть `content library`. Один MD при этом остаётся единственным источником правды для геймдизайнера, а генератор отвечает за маршрутизацию полей в нужный целевой файл.

### Принципы согласования слоёв

- При переводе области на MD-источник конвертация выполняется как **дозаполнение, а не урезание**. Если существующие рукописные литералы в `content library`, presentation-маппингах или смежных реестрах уже содержат более полный набор id/связей, чем текущий минимальный gameplay-срез, MD обязан завести этот полный набор и сгенерировать его дальше без потерь.
- То же правило применяется внутри одной области, когда один MD питает несколько целевых слоёв: итоговый MD отражает объединение уже существующих данных, а не пересечение. Например, если presentation-слой уже знает аудио-маппинг для нескольких weapon id, `content/weapons.md` заводит все эти weapon id как определения; если sample registry уже содержит отдельные пулы `hit`/`death`/`voice`, область enemies записывает их как разные значения, а не схлопывает до одного общего пула.
- Если «более полное» состояние нельзя выразить существующими публичными формами области, это стоп-сигнал на новое design-решение. Генератор не расширяет контракт по месту и не оставляет часть данных в рукописном `.ts` рядом с MD-источником.

### Внешние ассеты как источник derive-полей

- Помимо MD, генератор имеет право читать **бинарные ассеты под `public/**`** для derive-значений, которые не имеет смысла поддерживать вручную (например, фактический размер PNG в пикселях). Это единственное расширение «физических входов» генератора сверх MD.
- Конкретный набор derive-полей и алгоритм пересчёта живёт в **решении области** (для sprite visuals — в [sprite-assets.md](sprite-assets.md)). Этот файл фиксирует только устойчивые правила слоя: что derive-поле — это поле выходной публичной формы, чьё значение пересчитывается из ассета на каждом `content:build` и не фигурирует в MD.
- Для каждого derive-поля действует правило «без двух источников правды»:
  - в MD не должно быть колонки/ячейки, описывающей derive-поле; попытка завести такую колонку в области — ошибка генератора этой области (а не silent-merge);
  - в `<area>.generated.ts` derive-поле всегда пересчитано из текущего ассета, не из MD;
  - значение derive-поля **не** хранится в `client settings`, не уходит в snapshot и не закрепляется в любом другом долговечном месте — единственная точка хранения это сам ассет.
- Чтение бинарных ассетов оформляется отдельным util в `scripts/content-build/util/`: чистая функция `(absolutePath) → derived value`, без скрытого состояния, с понятным сообщением об ошибке `content/<area>.md row "<id>": <что не получилось> <path>: <reason>`. Util переиспользуется между областями; конкретные потребители — area-модули, не сам util.
- Атомарность из раздела «Архитектура генератора» распространяется без изменений: ошибка чтения бинарного ассета — тот же `atomic fail`, как и любая parse-ошибка MD. Ни один целевой `.generated.ts` не модифицируется, пока хотя бы один derive не разрешился.
- `content:check` ловит дрейф **по любому из физических входов**, не только по MD:
  - изменился MD, `.generated.ts` не пересобран → check падает (как сейчас);
  - изменился ассет (в т.ч. PNG переписан с другим размером), MD не менялся, `.generated.ts` не пересобран → check тоже падает, потому что повторный прогон генератора даст другие литералы.
  - Это единственный способ удержать инвариант «derive-поле всегда соответствует текущему ассету» на стороне CI.
- Ассеты, которые генератор читает только ради derive-полей, **не** становятся его «зависимостями списка областей»: список областей задаётся как раньше (`content/<area>.md`), а конкретные пути ассетов формируются area-модулем по содержимому MD (например, по колонке `image` или по inline-image-узлу — см. раздел «Inline media-узлы как derive-источники»).

### Multi-file области

- По умолчанию правило «один файл = одна область» из раздела «Источник правды и слои» — обязательное. Каждая область имеет один `content/<area>.md`, и каждое значение каждого поля каждой единицы этой области живёт в этом файле.
- В отдельных случаях, когда содержимое области состоит из **независимых единиц одного типа**, и каждая единица существенно богаче строки сравнительной таблицы (десятки полей, вложенные подкомпоненты, длинные списки или собственный список под-сущностей), область может быть разнесена на **папку** `content/<area>/` с одним MD-файлом на единицу. Такие области явно перечисляются в этом разделе; ввести multi-file область «по месту» в коде генератора без обновления этого файла запрещено.
- Список multi-file областей на момент этой ревизии:
  - `sessions` (`content/sessions/<presetId>.md`) — каждый файл описывает один пресет сессии целиком, включая метаданные пресета (`displayName`/`description`/`visibleInMenu`/`order`) и session-level таблицу фоновых изображений в партиции `# Session`, а также полный список encounter'ов в партиции `# Encounters` в порядке появления.
- Правила, обязательные для multi-file области:
  - имя файла без расширения = **id единицы** (`presetId` для sessions); опечатка в имени файла — отдельный id, не «продолжение» соседнего;
  - папка обходится в **отсортированном по имени файла** порядке; это даёт стабильный diff `<area>.generated.ts` независимо от ОС/файловой системы;
  - id единиц обязаны быть **уникальны кросс-файлово**; дублирование id в двух файлах — ошибка генератора, не silent-merge;
  - все правила partition-структуры (партиции определений и баланса или эквивалент по смыслу области), формы таблиц, derive-полей, inline media-узлов и shared resource set применяются **внутри каждого файла независимо**.
- Multi-file область имеет право на **cross-area references**: ячейки её MD могут ссылаться на стабильные id из других областей (`arenaId`, `playerId`, `weaponId`, `bossArchetypeId`, `archetypeId` спавнящихся врагов и т. п.). Такие ссылки обязаны валидироваться двумя независимыми путями:
  - на стороне **генератора**: area-парсер multi-file области импортирует уже сгенерированные `<other-area>.generated.ts` через обычный TS-import, экспонирует множества known id и валидирует ссылку с указанием `file:line:col` в MD; неизвестная ссылка — ошибка генератора, не runtime-фолбэк;
  - на стороне **сгенерированного файла**: `<area>.generated.ts` пишется как **прямые TS-импорты констант** другой области (например, `arena: SANDBOX_ARENA`), не как строковые id. Drift между MD multi-file области и реестрами других областей после этого ловит `tsc` поверх сгенерированного.
- Order областей в `AREAS` обязан размещать multi-file область **после** всех её зависимостей. На первом прогоне на свежем чекауте multi-file область читает зависимости из уже закоммиченных `<other-area>.generated.ts`; согласованные правки cross-area refs делаются одним атомарным PR (правка `content/<other-area>.md` + регенерация её `<other-area>.generated.ts` + правка соответствующего `content/<this-area>/<unit>.md` + регенерация `<this-area>.generated.ts`).
- Для области `sessions` партиция `# Session` имеет две таблицы:
  - первая таблица — `field | value`, обязательна, хранит метаданные и ссылки пресета (`displayName`/`description`/`visibleInMenu`/`order`/`arenaId`/`playerId`/`loadoutWeaponIds`/`selectedWeaponIndex`/`slimeFriendlyFire`/`winCondition`/`lossCondition`). `loadoutWeaponIds` — comma-list weapon id или `none`; `selectedWeaponIndex` — 0-based индекс в списке или `none` для holstered. Если `loadoutWeaponIds` равно `none`, `selectedWeaponIndex` тоже обязан быть `none`; если список не пуст, индекс обязан быть `none` или попадать внутрь списка. `slimeFriendlyFire` — `true`/`false` и рендерится в `SessionDefinition.rules.damage.slimeFriendlyFire`;
  - вторая таблица — `backgroundId | image`, обязательна, объявляет session-level фоновые изображения. `backgroundId` уникален внутри файла. Ячейка `image` обязана быть inline image-cell `![alt](../.../public/...)`; генератор валидирует URL по тем же правилам load-bearing inline image-узлов и пишет в generated/runtime один public-relative URL (`/images/bg/...`).
- В области `sessions` encounter-таблица `field | value` может иметь поле `backgroundId`. Для player-facing типов `wave`, `break`, `boss` поле обязательно и должно ссылаться на id из таблицы `# Session` `backgroundId | image`. Значение `none` разрешено только для non-player-facing bring-up/sandbox encounter'ов и даёт `null` в runtime-контракте. Неизвестный background id — ошибка генератора с привязкой к MD-ячейке.

### Inline media-узлы как derive-источники

Этот раздел дополняет правила «Внешние ассеты как источник derive-полей»: помимо колонки в таблице, путь к внешнему ассету может задаваться **inline media-узлом внутри H2 партиции определений**. Это альтернативная авторская поверхность для тех же derive-полей, и к ней применяются те же инварианты «без двух источников правды» и «атомарный fail».

- Media-узлы делятся на два вида с фиксированной разметкой:
  - **inline image-узел**: `![alt](url)` — стандартный markdown image syntax. Целевое derive-значение — путь к PNG-ассету и всё, что из него derive-ится (в т. ч. `sourceSizePx`/`worldSize`, см. [sprite-assets.md](sprite-assets.md));
  - **inline audio-link-узел**: `[link-text](url)` — стандартный markdown link syntax с текстом. Целевое derive-значение — `sampleId` для одного звукового события архетипа (на момент этой ревизии — `fire` у weapon-архетипов).
- Любой load-bearing media-узел области обязан удовлетворять следующим правилам, и нарушение — `atomic fail` генератора, аналогично parse-ошибке MD:
  - URL **обязан** быть относительным путём из текущего MD-файла к корневой папке `public/`: `../public/...` для `content/<area>.md`, `../../public/...` для `content/sessions/<presetId>.md` и аналогичный `../.../public/...` для более глубокой будущей раскладки. Это специальный path-relative-from-MD-формат, выбранный ровно потому, что только он рендерит ассет inline в распространённых MD-viewer-ах (GitHub PR, VS Code preview, IDE). Абсолютные пути (`/assets/...`), полные URL (`http(s)://...`) и любые другие префиксы — ошибка.
  - URL после strip части пути до `public/` обязан резолвиться в существующий файл на диске относительно корня репозитория. Несуществующий файл — ошибка с сообщением `content/<area>.md: section "## <id>": <expected> <path>: <reason>`.
  - URL, передаваемый в `.generated.ts` для рантайма, — это URL **после** одного strip части пути до `public/`. Рантайм видит уже public-relative path (`/assets/...`, `/sfx/...`), которым его кормит `Vite`. Strip — единственная конвертация; никаких алиасов, никакого rewrite по схеме.
- Для inline image-узла: link **alt** не несёт смысла для генератора (только для скринридера/автора) и валидации не подлежит. Источник правды о sprite-PNG — URL: путь к ассету и всё, что из него derive-ится.
- Для inline audio-link-узла: **link-text** — это и есть `sampleId`, то самое значение, под которое генератор записывает derive-поле в `.generated.ts`. URL — это обязательная вторая половина узла, выполняющая две функции одновременно: делает узел кликабельным для автора в MD-viewer-е и **cross-check** против `SampleRegistry`. Генератор валидирует сразу два инварианта:
  - link-text обязан существовать в `SampleRegistry` как `sampleId`;
  - URL после strip части пути до `public/` обязан **байт-в-байт** совпадать с `SampleRegistry[sampleId].url`. Несовпадение — ошибка с сообщением, в котором есть и фактический URL из MD, и ожидаемый URL из реестра. Это покрывает кейс «файл переименовали в реестре, забыли поправить MD» и «автор скопировал чужую ссылку, но забыл поменять подпись».
  - Reverse-lookup «URL → sampleId» **не используется**: link-text — единственный авторитетный источник `sampleId`, URL — лишь cross-check. Это решает проблему non-injective `SampleRegistry` (несколько `sampleId` могут указывать на один и тот же физический файл) без трогания контракта аудио-реестра.
- Запрет «двух источников правды» из раздела «Внешние ассеты как источник derive-полей» переносится без изменений: если область использует load-bearing media-узел для архетипа, MD этой области **не имеет права** заводить колонку или group в балансной партиции с тем же derive-полем для того же архетипа. Появление такой колонки/группы — ошибка генератора области, а не silent-merge с inline-узлом. Конкретный пример: после перевода области `enemies` на inline image-узлы группа `## Visual` с колонкой `image` в `# Balance` обязана исчезнуть — её повторное появление будет hard-error.
- Отсутствие load-bearing media-узла там, где область его требует, — ошибка генератора области (`expected ![…](…) under "## <id>"` / `expected [<sample-id>](…) under "## <id>"`). «Тихо пропустить, потому что не указано» — запрещено, как и для обязательной колонки.
- Семантика «опционального preview»-узла (тот же синтаксис, но игнорируется рантайм-генератором) сохраняется как **роль**, выбираемая областью на уровне вида узла. Область не имеет права использовать один и тот же вид узла (image / audio-link) одновременно как load-bearing для одних архетипов и как preview для других — это вело бы к неотличимым по форме узлам с разной семантикой и силой ошибок.
- Атомарность и `content:check` распространяются без изменений: ошибка любого инварианта inline-узла → `atomic fail`, никакого частичного обновления `.generated.ts`. Дрейф (URL поправили в MD, забыли пересобрать; PNG переписали с другим размером, MD не трогали) ловится тем же `content:check` через повторный прогон генератора.

### Shared resource set partition

В дополнение к двум стандартным партициям (определения и баланс) область может ввести **третий вид партиции** — shared resource set partition. Решение фиксирует общие правила формы и семантики; конкретное имя партиции (`# Sound sets`, `# Visual palettes`, `# Audio voice packs` и т. п.) выбирает область.

- Назначение: позволить группировать архетипы внутри **той же** области в именованные «наборы» и задавать одинаковые ресурсы (списки `sampleId`, цветовые палитры и т. п.) **один раз на набор**, а не повторять одну и ту же строку в карточке каждого архетипа. Это узкий read-side выигрыш для геймдизайнера; рантайм-формы не меняются.
- Партиция остаётся **локальной для области**: cross-MD-references (между `content/<area>.md` файлами) **out of scope** этого решения и потребуют отдельного design-расширения, если когда-нибудь понадобятся.
- Структура партиции (общие правила формата, обязательные для любой области, использующей паттерн):
  - заголовок партиции — H1 на любом языке; имя выбирает область;
  - первая H2 партиции — `## Members`, **обязательная** и **единственная**: задаёт принадлежность архетипов наборам. Шапка таблицы `setId | <members-column>`, имя колонки членов выбирает область (например `slimes`, `weapons`); вторая колонка — csv-список архетипных id по уже зафиксированному правилу «list-in-cell».
  - остальные H2-секции партиции — обычные узкие сравнительные таблицы по правилам балансной партиции (≤4 поля сверх ключевой колонки, GFM, hex-цвета, csv для list-полей), но **первая колонка = `setId`**, а не `id`. Каждая такая таблица параметризует все известные `setId` по одному из ресурсов набора.
  - значение ячейки в group-таблице, чей тип — `sampleId` (или его csv-список), допускает две равноправные формы: либо plain-текст (`slimes/hit-1`), либо **inline audio-link-узел** того же вида, что и в партиции определений (`[slimes/hit-1](../public/audio/slimes/hit-1.mp3)`). Во втором случае link-text — единственный авторитетный источник `sampleId`, URL валидируется по тем же двум инвариантам из раздела «Inline media-узлы как derive-источники» (относительный путь до `public/` со strip + байт-в-байт совпадение с `SampleRegistry[sampleId].url`). Смешивать обе формы внутри **одной** group-таблицы запрещено — выбор формы фиксируется на уровне таблицы (а не ячейки).
  - inline image-узлы (`![alt](url)`) в shared resource set partition **запрещены**: партиция группирует уже резолвящиеся id, а не сырые ассеты с derive-полями вроде `sourceSizePx`. Для таких ассетов остаётся только путь через H2 партиции определений.
- Инварианты, которые генератор области обязан проверять, и любое нарушение — `atomic fail`:
  - каждый архетип, существующий в партиции определений области, принадлежит **ровно одному** `setId` (ни нулю, ни двум). Архетип ни в одном `setId` — ошибка `archetype "<id>" is not a member of any set`. Архетип в двух `setId` — ошибка `archetype "<id>" is a member of multiple sets: …`.
  - каждый `setId`, упомянутый в любой группе партиции, объявлен в `## Members`. Незнакомый `setId` — reference-ошибка.
  - какие группы партиции считаются обязательными для каждого `setId` — решает область (например, для sound sets обязательны `## Hit`, `## Death`, `## Voice`); пропуск обязательной группы — ошибка генератора с указанием `setId` и группы.
  - значения внутри group-таблиц подчиняются обычным правилам области (sample-id обязан существовать в `SampleRegistry`, число — числу и т. п.).
- Семантика «развёртки» в выходных литералах: на render-фазе генератор **разворачивает N→1**: для каждого архетипа-члена записывается копия значений его set-а ровно в той же форме, в которой раньше эти значения писались напрямую. Архитектурное правило: рантайм-формы потребляющих слоёв (`Record<archetypeId, …>`, форма каждого значения) **не затрагиваются** — потребитель видит ровно те же литералы байт-в-байт.
- Сравнение с прежней схемой «строка-на-архетип» (когда тот же ресурс перечислялся в строке каждого архетипа): партиция — это всегда **второй** способ задать те же поля. Прежняя схема (колонки в балансной партиции) для этих полей в данной области **исчезает** — действует уже зафиксированное правило «без двух источников правды». Появление и колонки в `# Balance`, и shared resource set partition для одного и того же derive-поля — ошибка генератора области.
- Ввод shared resource set partition в новой области — это **расширение этого решения** (правка раздела «Shared resource set partition» с упоминанием новой области), а не «по месту» в области. Каждое расширение должно явно подтвердить, что: (a) рантайм-формы потребителя не меняются; (b) набор инвариантов выше применим без отступлений; (c) причина введения — реальная боль с дублированием, а не «удобнее писать».

### Пара «рукописный ↔ сгенерённый»

- Сгенерированные файлы кладутся **рядом** со своим рукописным потребителем, с суффиксом `.generated.ts`. Поддиректории `generated/` не создаются.
- Рукописный файл-потребитель сохраняет за собой: типы, реестры (`Record<id, Archetype>`), валидаторы, builder-функции, любую логику. Он импортирует сами литералы из `<area>.generated.ts`.
  - `src/shared/content/enemies.ts` остаётся владельцем `EnemyArchetype`, `validateEnemyRegistry`, `ENEMY_ARCHETYPES`. Литералы (`SLIME_FAST`, `SLIME_TANK`, `TRAINING_TARGET`) импортируются из `enemies.generated.ts`.
  - `src/main/audio/AudioMappings.ts` остаётся владельцем типов (`EnemyAudioMapping`, `VoiceSampleSpec`, …), `createAudioMappings`, валидаций sampleId через `SampleRegistry`. Литерал `ENEMY_AUDIO_MAPPINGS` импортируется из `enemyAudio.generated.ts`.
- В шапке каждого `.generated.ts` обязателен баннер «AUTO-GENERATED, не править руками», с явной ссылкой на исходный `content/<area>.md` и команду пересборки.

### Архитектура генератора

- Генератор живёт **вне `src/**`**, чтобы buildtime-код не попадал в рантайм-бандл. Решением вводится новая корневая директория `scripts/content-build/`. Это исключение из правила [web-stack.md](web-stack.md) о запрете на новые корневые каталоги — оно зафиксировано здесь явно и относится только к buildtime-инструментам, не к рантайму.
- Точка входа — `scripts/content-build/index.ts`, запускается через `tsx` (`tsx` добавляется в `devDependencies`). Один процесс генератора обходит все известные ему области.
- Конвейер генератора состоит из трёх фаз, исполняемых строго в этом порядке:
  1. **Parse**: каждый MD парсится через `micromark` + `mdast-util-from-markdown` + `micromark-extension-gfm-table` + `mdast-util-gfm-table` (всё dev-only; `micromark-extension-gfm-table` включает GFM table syntax, `mdast-util-gfm-table` проецирует его в mdast). AST проецируется в **input structure** — слабоструктурированное представление MD: дерево секций по H1/H2 заголовкам, для каждой таблицы — массив строк, в каждой строке — словарь «имя колонки → сырая строка». На этой фазе не делается никаких типовых проверок, никаких приведений — только «прочитать что есть». Ошибка фазы (битый MD, отсутствующая таблица там, где её ждали по H2) → `file:line` сообщение и выход с ненулевым кодом.
  2. **Render**: для каждой области отдельный TS-модуль под `scripts/content-build/<area>/` обходит input structure и формирует исходник каждого выходного `.ts`-файла. Рендеринг — обычные TS tagged template literals; внешний шаблонизатор не используется. Извлечение значений из input structure идёт через helper-функции (`requireSection`, `requireRow`, `requireCell`, `requireNumber`, `requireHexColor`, `requireSampleIdList` и аналогичные), которые при отсутствии или несоответствии формата бросают исключение с сообщением вида `content/<area>.md: section "## …" row "<id>" column "<name>": <ожидалось>`. Тип-приведения (например, `#RRGGBB` → числовой литерал `0xRRGGBB`, CSV → массив строк) живут внутри тех же helper-ов.
  3. **Write**: сначала весь набор выходных файлов формируется в памяти (или во временной директории); затем атомарно перезаписываются целевые `.ts` через rename. **Ни один целевой файл не модифицируется, если хотя бы одна область или один выходной файл не отрендерился успешно.** Частичная запись запрещена.
- Отдельного «валидатора» в генераторе нет. Структурный контракт между MD и кодом обеспечивают два слоя:
  - сами `requireX`-helper-ы — на ошибках формата падают с сообщением, привязанным к MD;
  - `tsc` поверх сгенерённого: каждый `.generated.ts` объявляет данные с публичным типом потребляющего слоя (`ReadonlyArray<EnemyArchetype>`, `Readonly<Record<string, EnemyAudioMapping>>` и т. п.); любой дрейф между MD/шаблоном/типом всплывает как compile-error в сгенерённом файле.
  - уже существующие рантайм-валидаторы (`validateEnemyRegistry`, `SampleRegistry.require` внутри `createAudioMappings`, и т. п.) остаются на месте как safety net — они продолжают работать поверх сгенерённых данных.

### Формат Markdown (общие правила формата)

Конкретные имена колонок и группы таблиц для каждой области задаются её собственным генератором; здесь фиксируются устойчивые правила формата, которые область не имеет права нарушать.

- Файл — обычный GFM Markdown.
- Секции H1 (`# …`) делят файл на верхнеуровневые **партиции**. Допускается до двух партиций на область: партиция определений (например `# Enemies`) и партиция балансных параметров (например `# Balance`). Конкретные имена партиций — деталь области; правило «H1 = партиция, H2 = единица внутри партиции» — общее.
- Внутри партиции определений: H2 (`## <id>`) объявляет одну сущность, где `<id>` — стабильный архетипный идентификатор, по которому идут ссылки везде. Внутри H2-секции допускаются:
  - inline media-узлы — image-ссылка `![alt](url)` и/или audio-link `[label](url)`. Каждый такой узел в области может играть одну из двух фиксированных ролей: «опциональный preview» (рантайм-генератор области игнорирует, узел нужен только автору) или «load-bearing derive-источник» (генератор области требует и валидирует — см. раздел «Inline media-узлы как derive-источники»). Роль каждого вида узла фиксирует область: один и тот же вид узла не может в одной области иногда быть preview, а иногда — load-bearing;
  - небольшая таблица `field | value` для полей, которые не имеют смысла в сравнении (например `displayName`, `color`).
- Внутри партиции балансных параметров: H2 (`## <group name>`) объявляет одну сравнительную таблицу. Каждая такая таблица обязана:
  - быть GFM-таблицей;
  - иметь первую колонку `id`, ссылающуюся на сущность из партиции определений;
  - быть **узкой**: не более пяти колонок (`id` + ≤4 поля). Более широкие наборы полей разносятся на две и более H2-секций по смыслу.
  - отсутствие строки в сравнительной таблице означает «поле для этого id не задано»; что значит «не задано», решает область (для аудио — пустой маппинг; для обязательного балансного числа — ошибка генератора).
- Любой `id`, упомянутый в любой сравнительной таблице, обязан существовать как H2 в партиции определений. Иначе генератор падает с reference-ошибкой.
- Цветовые значения в MD пишутся в web-нотации `#RRGGBB`. Генератор переводит их в эквивалентный числовой литерал `0xRRGGBB` в TS. Иные нотации (`0xRRGGBB`, `rgb(...)`) не принимаются.
- Списки идентификаторов внутри одной ячейки записываются через запятую (`slimes/hit-1, slimes/hit-2`). Это базовый разрешённый «list-in-cell» формат, и он применим только к полям, значение которых — список стабильных id (имена сэмплов, имена архетипов и т. п.). Контролируемые расширения этого формата — отдельный список ниже; иные мини-синтаксисы внутри ячейки запрещены.
- Контролируемые расширения «list-in-cell» (закрытый список, вводятся явно решением области и фиксируются здесь):
  - область `sessions`, override-таблица encounter-секции (см. «Несколько таблиц в одной H2-секции»), колонка `dropTable`: пары `dropArchetypeId:chance` через запятую (например, `heal-orb:0.20, magnet:0.05`). Разделитель внутри пары — двоеточие; пробелы вокруг `:` и `,` допустимы и игнорируются. Левая часть — стабильный `dropArchetypeId` (cross-area ref в область `drops`, валидируется тем же `requireDropRef`, что и обычные id-ссылки), правая — число в `[0, 1]`. Это единственное место, где «list-in-cell» допускает не-id-значения; добавление новых key-value пар в других областях требует расширения этого списка отдельным design-решением, не «по месту».
- Имена партиций и групп (текст H1/H2) могут быть на любом языке; маршрутизация генератора зависит от роли партиции (определения/баланс), а не от текста заголовка. Имена групп в балансной партиции выбирает автор области, генератор области знает, какую группу искать.

### Несколько таблиц в одной H2-секции

- По умолчанию H2-секция содержит **ровно одну** GFM-таблицу: `field | value` в партиции определений или одна сравнительная узкая таблица в партиции баланса. Это базовое правило раздела «Формат Markdown».
- Отдельно перечисленные области имеют право допускать в одной H2-секции более одной таблицы — каждая со своей **специальной сигнатурой заголовка** (имена колонок), по которой area-парсер их различает по позиции в наборе. Расширение оформляется явным разделом этого файла, не «по месту» в коде генератора.
- Список таких разрешений на момент этой ревизии:
  - область `sessions`, encounter-секция (внутри партиции `# Encounters` каждого `content/sessions/<presetId>.md`):
    - первая таблица — `field | value`, **обязательна**, общие параметры encounter'а с префиксами полей (`spawnKind`/`spawnIntervalMs`/`maxAlive`/`edgeMargin`, `zoneKind`/`zoneFromMargin`/`zoneToMargin`/`zoneDurationMs`, `transitionKind`/`transitionDurationMs`/`next`, `bossArchetypeId`/`bossSpawnPosition`/`bossEdgeMargin`);
    - вторая таблица — `seq | archetypeId` или `seq | archetypeId | x | y`, **условная**: обязательна при `spawnKind ∈ {wave, static}`, запрещена при `spawnKind ∈ {empty, boss}`. Сигнатура «первая колонка `seq`» используется генератором для отделения её от первой `field | value`-таблицы;
    - третья таблица — `seq | guaranteedDrops | dropTable | retaliationEnabled | retaliationDurationMs | loadoutWeaponIds | selectedWeaponIndex`, **полностью optional**: разрешена только при `spawnKind ∈ {wave, static}`, запрещена при `spawnKind ∈ {empty, boss}`. Каждая строка задаёт `SpawnOverride` для одного `seq` из второй таблицы; `seq` обязан существовать во второй таблице (иначе hard-error). Семантика и валидация полей override фиксируются в [spawn-overrides.md](spawn-overrides.md). Эта override-таблица — **единственное** контролируемое исключение из общего правила «узкая таблица: id + ≤4 поля» (см. «Формат Markdown»): ровно для неё разрешено `seq` + 6 полей в фиксированном порядке колонок. Расширение этой таблицы новыми колонками — отдельная правка этого решения и [spawn-overrides.md](spawn-overrides.md), не «по месту». Допустимые значения ячеек: `guaranteedDrops` — `none` (поле override опущено) или csv `dropArchetypeId`-ов; `dropTable` — `none` (поле override опущено), `empty` (override `[]`) или key-value csv `dropArchetypeId:chance` (см. контролируемое расширение «list-in-cell»); `retaliationEnabled` — `none` или `true`/`false`; `retaliationDurationMs` — `none` или целое `>= 0`; `loadoutWeaponIds` — `none` (поле override опущено) или csv `weaponArchetypeId`-ов (cross-area ref в область `weapons`, валидируется тем же путём, что `requireDropRef` для область `drops`); `selectedWeaponIndex` — `none` (поле override опущено) или целое в `[0, loadoutWeaponIds.length)`, либо `null` для holstered. Если `retaliationEnabled = none`, то и `retaliationDurationMs` обязан быть `none`, и наоборот — обе колонки задают одно поле `SpawnOverride.retaliation` целиком, частичная задача запрещена. То же правило для `loadoutWeaponIds` и `selectedWeaponIndex`: если одна из колонок равна `none`, вторая обязана быть `none` тоже — обе колонки задают одно поле `SpawnOverride.loadout` целиком, и частично заданный loadout запрещён. Сигнатура «первая колонка `seq` плюс точно эти шесть имён колонок в этом порядке» используется генератором для отличия третьей таблицы от второй.
- Правила, обязательные для области, использующей несколько таблиц в H2:
  - каждая допустимая таблица определена сигнатурой первой строки заголовка и набором обязательных колонок; перепутанная сигнатура (например, `seq` вместо `field` в первой таблице) — ошибка генератора, а не «вторая таблица того же типа»;
  - правило «узкая таблица: id + ≤4 поля» из «Формат Markdown» сохраняется для **каждой** из таблиц H2-секции по отдельности; нельзя обойти лимит, разнеся одно сравнение на две таблицы того же типа. Единственное исключение фиксируется явно в перечислении выше (override-таблица области `sessions`, `seq` + 6 полей); другие исключения вводятся только обновлением этого раздела, не «по месту»;
  - условные обязательность/запрет (как для второй и третьей таблицы в encounter-секции `sessions`) фиксируются в этом разделе явно по парам (значение поля в первой таблице → требование к существованию каждой следующей таблицы);
  - подсекции через H3 для разнесения данных внутри H2 не вводятся: парсер H1/H2-only остаётся единой инвариантной формой.

### Интеграция в сборку

Существующие npm-скрипты сохраняются: `dev = vite`, `build = tsc -p tsconfig.json && tsc -p tsconfig.worker.json && vite build`, `typecheck`, `test`, `test:watch`, `preview` — без изменений. Решение добавляет три новых скрипта и расширяет два существующих **композицией**, не заменой:

- `content:build` запускает генератор. При успехе — атомарно перезаписывает все `.generated.ts`. При любой ошибке — пишет ничего, выходит с ненулевым кодом и сообщением `content/<area>.md:…`.
- `content:check` запускает генератор во временную директорию и сравнивает результат с закоммиченными `.generated.ts`. Любой дифф = exit non-zero. Это «дрейфовый» гейт.
- `predev` = `content:build`. Благодаря npm-lifecycle он автоматически запускается перед `npm run dev`, и dev-цикл геймдизайнера — «поправил MD → `npm run dev` → видит» — без отдельной команды.
- `tsconfig.scripts.json` проверяет buildtime-код генератора в `scripts/**` теми же strict-правилами TypeScript, что и runtime-проекты. Генератор запускается через `tsx`, но `tsx` не заменяет `tsc`-проверку источников генератора.
- `build` расширяется до `tsc -p tsconfig.scripts.json && npm run content:check && tsc -p tsconfig.json && tsc -p tsconfig.worker.json && vite build`. Проверка `scripts/**` стоит первой, потому что `content:check` исполняет генератор и должен запускаться уже после typecheck самого buildtime-инструмента. Затем `content:check` ловит дрейф `.generated.ts` до runtime-`tsc` и `vite build`; два исходных runtime-`tsc` шага остаются перед `vite build` в прежнем порядке.
- CLI генератора фиксирует repository root относительно `scripts/content-build/index.ts` перед чтением `content/**` и записью `.generated.ts`. Поэтому прямой запуск `tsx /path/to/repo/scripts/content-build/index.ts` не зависит от текущей директории shell.
- Сами `.generated.ts` файлы **коммитятся** в репозиторий. Это нужно одновременно для трёх вещей: чтобы `npm install && npm run dev` работал на свежем чекауте без отдельного шага; чтобы PR-ревью видел и diff MD, и diff литералов; чтобы `content:check` имел против чего сравнивать.

### Запрещённые шаблоны

- Никаких «тихих» дефолтов в генераторе: пропуск обязательного поля → ошибка, не подстановка.
- Никаких ручных правок в `.generated.ts`. Баннер в шапке об этом сообщает, ревью это блокирует.
- Никаких «MD имеет поле, которое рантайм игнорирует» сверх явных ролей, зафиксированных областью: каждый вид inline media-узла в области либо целиком preview, либо целиком load-bearing (см. раздел «Inline media-узлы как derive-источники»). Ввести новый игнорируемый вид узла = обновить этот документ.
- Никакого смешения генераторного и рантайм-кода под `src/**`. Генератор целиком живёт в `scripts/content-build/**` и из `src/**` не импортируется. Если генератору нужен общий тип с рантаймом (например `EnemyArchetype`), он импортирует его из `src/shared/**` — направление импортов односторонее.
- Никакого MD-файла на одну область, который превращается в два разных источника правды (например «часть полей в MD, часть в рукописном `.ts` рядом»). Если поле этой области управляется MD — все его значения для всех id живут в этом MD.
- Никакой MD-колонки/ячейки для derive-поля, которое получается из внешнего ассета (см. раздел «Внешние ассеты как источник derive-полей»). Появление такой колонки в MD — ошибка генератора области, а не silent-merge с derived value. То же правило действует для load-bearing inline media-узлов: если область получает sprite-PNG/`fire`-sampleId через inline image-/audio-link-узел, MD-колонка с тем же derive-полем для того же архетипа — ошибка генератора (см. раздел «Inline media-узлы как derive-источники»).
- Никаких URL-ов в load-bearing media-узлах, не подчиняющихся правилу «относительный путь из MD до `public/` + один strip → public-relative path». Любые иные схемы URL (`http(s)://`, `/`, `./`, alias-схемы) — ошибка.
- Никакого использования shared resource set partition для derive-поля, которое уже задаётся колонкой в балансной партиции той же области, и наоборот. Параллельные источники одного и того же поля — `atomic fail` генератора.
- Никаких inline image-узлов внутри shared resource set partition: разрешены только plain-`sampleId` или inline audio-link-ячейки в `sampleId`-колонках (см. соответствующее правило раздела «Shared resource set partition»).
- Никакого смешения двух форм `sampleId`-ячейки (plain vs inline audio-link) внутри одной group-таблицы shared resource set partition. Форма фиксируется на уровне таблицы.
- Никакой multi-file раскладки (`content/<area>/*.md`) для области, не упомянутой явно в разделе «Multi-file области». Появление папки `content/<area>/` для области, у которой уже есть `content/<area>.md` (или для новой области без обновления этого документа), — ошибка генератора, а не «расширение по умолчанию». Это удерживает правило «один файл = одна область» как базовое; попадание области в multi-file список — отдельное архитектурное решение через обновление этого файла.
- Никаких H2-секций с более чем одной GFM-таблицей в области, не упомянутой явно в разделе «Несколько таблиц в одной H2-секции». Появление второй (или, для области с разрешением на две таблицы, — третьей) таблицы в H2 такой области без явного расширения этого раздела — ошибка генератора, а не silent-merge. Это удерживает правило «одна H2 = одна таблица» как базовое.
- Никаких cross-area references за пределами multi-file областей: одно-файловая область не имеет права ссылаться по id на сущности другой области, даже если область-цель уже сгенерирована. Cross-area refs — расширение, привязанное к multi-file модели; ввод их «по месту» в одно-файловую область — ошибка генератора. Если у одно-файловой области появилась реальная нужда в cross-area refs — это кандидат на перевод в multi-file область, а не на «тихое» расширение.

## Consequences

- Геймдизайнер правит баланс одной области, открывая ровно один MD-файл, и видит результат после `npm run dev` (или явного `npm run content:build` + перезапуска).
- Рантайм-контракты и их валидаторы остаются неизменными; поведение игры после первой генерации эквивалентно текущему по литералам.
- `tsc` на сгенерённых файлах автоматически ловит любой дрейф между MD/шаблоном и публичным типом потребляющего слоя — раньше runtime-выполнения и ближе к месту изменения.
- Добавление новой контентной области сводится к шаблону: положить `content/<area>.md`, написать `scripts/content-build/<area>/` (parse-проекция и render шаблонов), повесить на ту же атомарную фазу записи и тот же `content:build`. Новых архитектурных решений для типичной области не требуется; нестандартные требования (несколько целевых слоёв, нестандартные мини-форматы) заводят дополнение к этому документу или новое решение.
- CI/Vercel-деплой защищён `tsconfig.scripts.json` и `content:check` в начале `build`: сначала проверяется сам генератор, затем дрейф становится build-time-ошибкой, а не runtime-несовместимостью.
- Появляется одна новая корневая директория `scripts/`. Это **разрешено** этим решением и не открывает дверь для новых корневых директорий «по месту»: правило `web-stack.md` про `src/**` не нарушается, и любые будущие top-level каталоги по-прежнему требуют отдельного решения.
- Сгенерированные `.generated.ts` лежат в репозитории — растёт объём diff в PR с правкой баланса (видно и MD, и сгенерённый дельту), но снижается риск «забыли пересобрать».
- Авторская поверхность для sprite-/звук-областей становится визуально-богатой: открыв `content/<area>.md` в любом MD-viewer-е, геймдизайнер видит картинки и кликабельные звуки прямо под H2 архетипа. Цена — два инварианта на каждый load-bearing media-узел («относительный путь до `public/`», «link-text == `sampleId` из `SampleRegistry` + URL == `SampleRegistry[sampleId].url`»), которые область обязана честно валидировать.
- Shared resource set partition даёт областям **локальный** механизм дедупликации идентичных списков ресурсов (один `default` sound-set покрывает 30 архетипов одной строкой) без каких-либо изменений в рантайм-формах потребителя. Расширение паттерна на новые области — отдельная правка этого решения, не «по месту».
- Multi-file области (раскладка `content/<area>/*.md`) расширяют модель «один файл = одна область» точечно для случаев, где единица сложнее строки сравнительной таблицы и заслуживает целого файла (сейчас — пресет сессии). Ценой становится новая ответственность области валидировать кросс-файловую уникальность id и порядок обхода файлов; выгодой — авторский фокус «один пресет = один файл», без свалки длинных таблиц по разным пресетам в одном MD. Cross-area references как часть multi-file области валидируются дважды (area-парсер по `file:line` + `tsc` поверх сгенерированного), что устраняет «тихий» drift между MD одной области и реестрами другой.
