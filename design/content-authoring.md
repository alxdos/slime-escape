# Content Authoring (Markdown Sources)

- Status: accepted
- Created: 2026-04-23
- Updated: 2026-04-23 (story 013: добавлен раздел «Внешние ассеты как источник derive-полей», запрет MD-колонок для derive-полей, players включён в перечисление известных областей; story 012: добавлено правило «дозаполнение, а не урезание» при согласовании MD-источников с уже существующими слоями)

## Context

Сегодня контент игры (архетипы врагов, оружие, дроп, боссы, игрок, арены, preset-ы, сборка сессии, маппинги аудио на архетипы) живёт как TS-литералы, разнесённые по `src/shared/content/**` и `src/main/audio/AudioMappings.ts`. Любая правка баланса = правка TypeScript: PR-ревью смешивает «изменили число» и «изменили логику», а у геймдизайнера нет отдельной поверхности, которая бы позволяла менять параметры, не открывая код.

Нужна авторская поверхность для геймдизайнера со следующими свойствами:

- один Markdown-файл = один контентный область (slimes/enemies, sessions, weapons, …);
- генератор времени сборки превращает MD в те же TS-литералы, что и сейчас, без изменений в потребителях;
- рантайм-контракты (`EnemyArchetype`, `AudioMappings.EnemyAudioMapping`, …) и их валидаторы не меняются;
- ошибка в MD не приводит к молчаливой подмене или частичному писанию: либо всё валидно и переписано атомарно, либо файлы остаются как были и сборка падает с понятным сообщением;
- сгенерённое не дрейфует от MD: нет «MD сказали одно, в репозитории сгенерённое другое».

Решение фиксирует устойчивые правила этого слоя; конкретный набор полей конкретной области (имена колонок, какие группы балансных таблиц, и т. п.) принадлежит самой области и её истории, а не этому документу.

## Decision

### Источник правды и слои

- Для каждой контентной области, которой управляет MD-источник, существует **один** файл `content/<area>.md` в корневой директории `content/`. Это единственное место, где геймдизайнер меняет данные этой области. Первая такая область — `content/enemies.md` (включая стационарные мишени). Последующие области (`weapons`, `drops`, `bosses`, `players`, `sessions`, `arenas`, `presets`) добавляются отдельными историями, каждая со своим `content/<area>.md`. На момент этой ревизии живы области `enemies`, `weapons`, `drops`, `bosses` (после 011/012) и `players` (история 013).
- Один MD-файл может производить **один или несколько** сгенерированных `.ts`-файлов, размещённых **в том слое, который данные потребляет**, а не в одном «свалочном» каталоге generated. Для области enemies это:
  - балансные/контентные поля `EnemyArchetype` → `src/shared/content/enemies.generated.ts` (`content library`, sim-сторона);
  - аудио-маппинг (`hit/death sampleIds`, `voice` sampleIds + интервалы) → `src/main/audio/enemyAudio.generated.ts` (presentation, main-сторона).
- Это разделение обязательно и фиксирует границу из [content-boundaries.md](content-boundaries.md): аудио — это presentation, не часть `content library`. Один MD при этом остаётся единственным источником правды для геймдизайнера, а генератор отвечает за маршрутизацию полей в нужный целевой файл.

### Принципы согласования слоёв

- При переводе области на MD-источник конвертация выполняется как **дозаполнение, а не урезание**. Если существующие рукописные литералы в `content library`, presentation-маппингах или смежных реестрах уже содержат более полный набор id/связей, чем текущий минимальный gameplay-срез, MD обязан завести этот полный набор и сгенерировать его дальше без потерь.
- То же правило применяется внутри одной области, когда один MD питает несколько целевых слоёв: итоговый MD отражает объединение уже существующих данных, а не пересечение. Например, если presentation-слой уже знает аудио-маппинг для нескольких weapon id, `content/weapons.md` заводит все эти weapon id как определения; если sample registry уже содержит отдельные пулы `hit`/`death`/`voice`, область enemies записывает их как разные значения, а не схлопывает до одного общего пула.
- Если «более полное» состояние нельзя выразить существующими публичными формами области, это стоп-сигнал на новое design-решение. Генератор не расширяет контракт по месту и не оставляет часть данных в рукописном `.ts` рядом с MD-источником.

### Внешние ассеты как источник derive-полей

- Помимо MD, генератор имеет право читать **бинарные ассеты под `public/**`** для derive-значений, которые не имеет смысла поддерживать вручную (например, фактический размер PNG в пикселях). Это единственное расширение «физических входов» генератора сверх MD.
- Конкретный набор derive-полей и алгоритм пересчёта живёт в **решении области** (для sprite visuals — в [sprite-assets.md](sprite-assets.md)). Этот файл фиксирует только устойчивые правила слоя: что derive-поле — это поле выходной публичной формы, чьё значение пересчитывается из ассета на каждом `content:build` и не фигурирует в MD.
- Для каждого derive-поля действует правило «без двух источников правды»:
  - в MD не должно быть колонки/ячейки, описывающей derive-поле; попытка завести такую колонку в области — ошибка генератора этой области (а не silent-merge);
  - в `<area>.generated.ts` derive-поле всегда пересчитано из текущего ассета, не из MD;
  - значение derive-поля **не** хранится в `client settings`, не уходит в snapshot и не закрепляется в любом другом долговечном месте — единственная точка хранения это сам ассет.
- Чтение бинарных ассетов оформляется отдельным util в `scripts/content-build/util/`: чистая функция `(absolutePath) → derived value`, без скрытого состояния, с понятным сообщением об ошибке `content/<area>.md row "<id>": <что не получилось> <path>: <reason>`. Util переиспользуется между областями; конкретные потребители — area-модули, не сам util.
- Атомарность из раздела «Архитектура генератора» распространяется без изменений: ошибка чтения бинарного ассета — тот же `atomic fail`, как и любая parse-ошибка MD. Ни один целевой `.generated.ts` не модифицируется, пока хотя бы один derive не разрешился.
- `content:check` ловит дрейф **по любому из физических входов**, не только по MD:
  - изменился MD, `.generated.ts` не пересобран → check падает (как сейчас);
  - изменился ассет (в т.ч. PNG переписан с другим размером), MD не менялся, `.generated.ts` не пересобран → check тоже падает, потому что повторный прогон генератора даст другие литералы.
  - Это единственный способ удержать инвариант «derive-поле всегда соответствует текущему ассету» на стороне CI.
- Ассеты, которые генератор читает только ради derive-полей, **не** становятся его «зависимостями списка областей»: список областей задаётся как раньше (`content/<area>.md`), а конкретные пути ассетов формируются area-модулем по содержимому MD (например, по колонке `image`).

### Пара «рукописный ↔ сгенерённый»

- Сгенерированные файлы кладутся **рядом** со своим рукописным потребителем, с суффиксом `.generated.ts`. Поддиректории `generated/` не создаются.
- Рукописный файл-потребитель сохраняет за собой: типы, реестры (`Record<id, Archetype>`), валидаторы, builder-функции, любую логику. Он импортирует сами литералы из `<area>.generated.ts`.
  - `src/shared/content/enemies.ts` остаётся владельцем `EnemyArchetype`, `validateEnemyRegistry`, `ENEMY_ARCHETYPES`. Литералы (`SLIME_FAST`, `SLIME_TANK`, `TRAINING_TARGET`) импортируются из `enemies.generated.ts`.
  - `src/main/audio/AudioMappings.ts` остаётся владельцем типов (`EnemyAudioMapping`, `VoiceSampleSpec`, …), `createAudioMappings`, валидаций sampleId через `SampleRegistry`. Литерал `ENEMY_AUDIO_MAPPINGS` импортируется из `enemyAudio.generated.ts`.
- В шапке каждого `.generated.ts` обязателен баннер «AUTO-GENERATED, не править руками», с явной ссылкой на исходный `content/<area>.md` и команду пересборки.

### Архитектура генератора

- Генератор живёт **вне `src/**`**, чтобы buildtime-код не попадал в рантайм-бандл. Решением вводится новая корневая директория `scripts/content-build/`. Это исключение из правила [web-stack.md](web-stack.md) о запрете на новые корневые каталоги — оно зафиксировано здесь явно и относится только к buildtime-инструментам, не к рантайму.
- Точка входа — `scripts/content-build/index.ts`, запускается через `tsx` (`tsx` добавляется в `devDependencies`). Один процесс генератора обходит все известные ему области.
- Конвейер генератора состоит из трёх фаз, исполняемых строго в этом порядке:
  1. **Parse**: каждый MD парсится через `micromark` + `mdast-util-from-markdown` + `micromark-extension-gfm-table` + `mdast-util-gfm-table` (всё dev-only; `micromark-extension-gfm-table` включает GFM table syntax, `mdast-util-gfm-table` проецирует его в mdast). AST проецируется в **input structure** — слабоструктурированное представление MD: дерево секций по H1/H2 заголовкам, для каждой таблицы — массив строк, в каждой строке — словарь «имя колонки → сырая строка». На этой фазе не делается никаких типовых проверок, никаких приведений — только «прочитать что есть». Ошибка фазы (битый MD, отсутствующая таблица там, где её ждали по H2) → `file:line` сообщение и выход с ненулевым кодом.
  2. **Render**: для каждой области отдельный TS-модуль под `scripts/content-build/<area>/` обходит input structure и формирует исходник каждого выходного `.ts`-файла. Рендеринг — обычные TS tagged template literals; внешний шаблонизатор не используется. Извлечение значений из input structure идёт через helper-функции (`requireSection`, `requireRow`, `requireCell`, `requireNumber`, `requireHexColor`, `requireSampleIdList` и аналогичные), которые при отсутствии или несоответствии формата бросают исключение с сообщением вида `content/<area>.md: section "## …" row "<id>" column "<name>": <ожидалось>`. Тип-приведения (например, `#RRGGBB` → числовой литерал `0xRRGGBB`, CSV → массив строк) живут внутри тех же helper-ов.
  3. **Write**: сначала весь набор выходных файлов формируется в памяти (или во временной директории); затем атомарно перезаписываются целевые `.ts` через rename. **Ни один целевой файл не модифицируется, если хотя бы одна область или один выходной файл не отрендерился успешно.** Частичная запись запрещена.
- Отдельного «валидатора» в генераторе нет. Структурный контракт между MD и кодом обеспечивают два слоя:
  - сами `requireX`-helper-ы — на ошибках формата падают с сообщением, привязанным к MD;
  - `tsc` поверх сгенерённого: каждый `.generated.ts` объявляет данные с публичным типом потребляющего слоя (`ReadonlyArray<EnemyArchetype>`, `Readonly<Record<string, EnemyAudioMapping>>` и т. п.); любой дрейф между MD/шаблоном/типом всплывает как compile-error в сгенерённом файле.
  - уже существующие рантайм-валидаторы (`validateEnemyRegistry`, `SampleRegistry.require` внутри `createAudioMappings`, и т. п.) остаются на месте как safety net — они продолжают работать поверх сгенерённых данных.

### Формат Markdown (общие правила формата)

Конкретные имена колонок и группы таблиц для каждой области задаются её собственным генератором; здесь фиксируются устойчивые правила формата, которые область не имеет права нарушать.

- Файл — обычный GFM Markdown.
- Секции H1 (`# …`) делят файл на верхнеуровневые **партиции**. Допускается до двух партиций на область: партиция определений (например `# Enemies`) и партиция балансных параметров (например `# Balance`). Конкретные имена партиций — деталь области; правило «H1 = партиция, H2 = единица внутри партиции» — общее.
- Внутри партиции определений: H2 (`## <id>`) объявляет одну сущность, где `<id>` — стабильный архетипный идентификатор, по которому идут ссылки везде. Внутри H2-секции допускаются:
  - опциональная ссылка-картинка вида `![…](…)` — на момент этой ревизии используется только как preview для авторов; рантайм её игнорирует;
  - небольшая таблица `field | value` для полей, которые не имеют смысла в сравнении (например `displayName`, `color`).
- Внутри партиции балансных параметров: H2 (`## <group name>`) объявляет одну сравнительную таблицу. Каждая такая таблица обязана:
  - быть GFM-таблицей;
  - иметь первую колонку `id`, ссылающуюся на сущность из партиции определений;
  - быть **узкой**: не более пяти колонок (`id` + ≤4 поля). Более широкие наборы полей разносятся на две и более H2-секций по смыслу.
  - отсутствие строки в сравнительной таблице означает «поле для этого id не задано»; что значит «не задано», решает область (для аудио — пустой маппинг; для обязательного балансного числа — ошибка генератора).
- Любой `id`, упомянутый в любой сравнительной таблице, обязан существовать как H2 в партиции определений. Иначе генератор падает с reference-ошибкой.
- Цветовые значения в MD пишутся в web-нотации `#RRGGBB`. Генератор переводит их в эквивалентный числовой литерал `0xRRGGBB` в TS. Иные нотации (`0xRRGGBB`, `rgb(...)`) не принимаются.
- Списки идентификаторов внутри одной ячейки записываются через запятую (`slimes/hit-1, slimes/hit-2`). Это единственный разрешённый «list-in-cell» формат, и он применим только к полям, значение которых — список стабильных id (имена сэмплов, имена архетипов и т. п.). Любые иные мини-синтаксисы внутри ячейки запрещены.
- Имена партиций и групп (текст H1/H2) могут быть на любом языке; маршрутизация генератора зависит от роли партиции (определения/баланс), а не от текста заголовка. Имена групп в балансной партиции выбирает автор области, генератор области знает, какую группу искать.

### Интеграция в сборку

Существующие npm-скрипты сохраняются: `dev = vite`, `build = tsc -p tsconfig.json && tsc -p tsconfig.worker.json && vite build`, `typecheck`, `test`, `test:watch`, `preview` — без изменений. Решение добавляет три новых скрипта и расширяет два существующих **композицией**, не заменой:

- `content:build` запускает генератор. При успехе — атомарно перезаписывает все `.generated.ts`. При любой ошибке — пишет ничего, выходит с ненулевым кодом и сообщением `content/<area>.md:…`.
- `content:check` запускает генератор во временную директорию и сравнивает результат с закоммиченными `.generated.ts`. Любой дифф = exit non-zero. Это «дрейфовый» гейт.
- `predev` = `content:build`. Благодаря npm-lifecycle он автоматически запускается перед `npm run dev`, и dev-цикл геймдизайнера — «поправил MD → `npm run dev` → видит» — без отдельной команды.
- `tsconfig.scripts.json` проверяет buildtime-код генератора в `scripts/**` теми же strict-правилами TypeScript, что и runtime-проекты. Генератор запускается через `tsx`, но `tsx` не заменяет `tsc`-проверку источников генератора.
- `build` расширяется до `tsc -p tsconfig.scripts.json && npm run content:check && tsc -p tsconfig.json && tsc -p tsconfig.worker.json && vite build`. Проверка `scripts/**` стоит первой, потому что `content:check` исполняет генератор и должен запускаться уже после typecheck самого buildtime-инструмента. Затем `content:check` ловит дрейф `.generated.ts` до runtime-`tsc` и `vite build`; два исходных runtime-`tsc` шага остаются перед `vite build` в прежнем порядке.
- CLI генератора фиксирует repository root относительно `scripts/content-build/index.ts` перед чтением `content/**` и записью `.generated.ts`. Поэтому прямой запуск `tsx /path/to/repo/scripts/content-build/index.ts` не зависит от текущей директории shell.
- Сами `.generated.ts` файлы **коммитятся** в репозиторий. Это нужно одновременно для трёх вещей: чтобы `npm install && npm run dev` работал на свежем чекауте без отдельного шага; чтобы PR-ревью видел и diff MD, и diff литералов; чтобы `content:check` имел против чего сравнивать.

### Запрещённые шаблоны

- Никаких «тихих» дефолтов в генераторе: пропуск обязательного поля → ошибка, не подстановка.
- Никаких ручных правок в `.generated.ts`. Баннер в шапке об этом сообщает, ревью это блокирует.
- Никаких «MD имеет поле, которое рантайм игнорирует» сверх явно перечисленных опциональных (на момент этой ревизии — только превью-картинка в партиции определений). Ввести новое игнорируемое поле = обновить этот документ.
- Никакого смешения генераторного и рантайм-кода под `src/**`. Генератор целиком живёт в `scripts/content-build/**` и из `src/**` не импортируется. Если генератору нужен общий тип с рантаймом (например `EnemyArchetype`), он импортирует его из `src/shared/**` — направление импортов односторонее.
- Никакого MD-файла на одну область, который превращается в два разных источника правды (например «часть полей в MD, часть в рукописном `.ts` рядом»). Если поле этой области управляется MD — все его значения для всех id живут в этом MD.
- Никакой MD-колонки/ячейки для derive-поля, которое получается из внешнего ассета (см. раздел «Внешние ассеты как источник derive-полей»). Появление такой колонки в MD — ошибка генератора области, а не silent-merge с derived value.

## Consequences

- Геймдизайнер правит баланс одной области, открывая ровно один MD-файл, и видит результат после `npm run dev` (или явного `npm run content:build` + перезапуска).
- Рантайм-контракты и их валидаторы остаются неизменными; поведение игры после первой генерации эквивалентно текущему по литералам.
- `tsc` на сгенерённых файлах автоматически ловит любой дрейф между MD/шаблоном и публичным типом потребляющего слоя — раньше runtime-выполнения и ближе к месту изменения.
- Добавление новой контентной области сводится к шаблону: положить `content/<area>.md`, написать `scripts/content-build/<area>/` (parse-проекция и render шаблонов), повесить на ту же атомарную фазу записи и тот же `content:build`. Новых архитектурных решений для типичной области не требуется; нестандартные требования (несколько целевых слоёв, нестандартные мини-форматы) заводят дополнение к этому документу или новое решение.
- CI/Vercel-деплой защищён `tsconfig.scripts.json` и `content:check` в начале `build`: сначала проверяется сам генератор, затем дрейф становится build-time-ошибкой, а не runtime-несовместимостью.
- Появляется одна новая корневая директория `scripts/`. Это **разрешено** этим решением и не открывает дверь для новых корневых директорий «по месту»: правило `web-stack.md` про `src/**` не нарушается, и любые будущие top-level каталоги по-прежнему требуют отдельного решения.
- Сгенерированные `.generated.ts` лежат в репозитории — растёт объём diff в PR с правкой баланса (видно и MD, и сгенерённый дельту), но снижается риск «забыли пересобрать».
